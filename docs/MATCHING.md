# Transformer + 异构图双边推荐

## 项目中的实际实现

当前部署版本是三个小模型的集成，总计 **54,678 个参数**。每个模型使用字符级嵌入与可学习位置嵌入 → 1 层、4 个注意力头、16 维 Transformer Encoder → 1 层按关系分别参数化的异构图传播 → 双向 MLP 评分头。训练 dropout 为 0.1，推理关闭。初版的 84,674 参数单模型保留在 `server/models/matching_v1.pt`，用于对照。

项目已根据 [一层与两层 Encoder 的实测对照](ENCODER_DEPTH.md) 选定上述一层轻量方案：单成员 18,226 个参数，维持三个成员集成。选择依据是两层未取得稳定的质量提升，且本机前向推理开销更高。

这是一种轻量的 **Transformer 文本编码 + relational heterogeneous GNN** 组合，不是完整 HGT 论文模型，也不是预训练语言模型。它没有调用外部大模型，不具备可声称的通用中文语义理解能力。

图包含旅人行程、地陪服务、城市、服务类型、语言、兴趣、节奏七类节点。十种正向关系以及相应反向关系分别有自己的线性变换参数，例如 `traveler_interest` 和 `guide_interest` 不共用关系参数。图里没有把训练目标或待预测的“接受”关系作为输入边。

单层图传播把城市、服务、兴趣等属性传入双方节点表示。评分头同时接收文本表示、图表示、逐元素交互，以及四个可观察的相容性特征：服务覆盖率、共同兴趣分别占双方兴趣的比例、节奏是否相交。这些是填写信息的特征工程，不是隐藏训练标签。三个独立随机种子的模型分别输出两方向分数，再平均，最后计算综合分：

- T：旅人视角的地陪推荐分。
- G：地陪视角的行程推荐分。
- 双边分：`2 × T × G / (T + G)`，即调和平均。单边很高而另一边很低时，不会成为高分组合。

输出乘以 100 只是显示尺度，不是成功率、接受概率或经校准的满意度。理由列表只解释已验证的条件与共同属性，不伪装成模型注意力的因果解释。分数用于双向候选排序，不执行一对一稳定分配，也不会替任何一方确认预约。

## 双方需要提供的信息

旅人：城市、日期、开始时间、套餐时长、人数、整团总预算、需要的服务、可沟通语言、兴趣、节奏与一段需求文字。保存前须明确同意向符合条件的地陪展示这些信息；不显示邮箱。

地陪：沿用已有服务城市、套餐与沟通语言；另填最大接待人数、可接单星期、休息日期、希望接待的旅行兴趣与节奏、文字偏好。每条服务独立设置。旧服务未提供这些信息时，会被标为“地陪尚未填写双边偏好”，不生成虚构的地陪评分。

先按硬条件过滤：城市、服务、共同语言、套餐时长、整团预算（含超过四人的费用）、最大人数、接单星期、休息日期及已有预约时间重叠。星期与休息日期按出发日判断。相同地陪账号的不同服务共享档期；待确认或已确认预约均占用时段，取消后释放。冲突检查按实际起止时间，跨午夜重叠也能识别。现在创建预约也使用同一档期检查。

双方视图使用同一组开放行程和服务构建图，因此同一时刻同一对行程/服务的双向分数一致。行程撤回后不再参与地陪推荐；已有聊天与预约保留。地陪可以从符合条件的行程创建会话并联系旅人。

## 安装、训练与运行

基础功能仍可仅用 Python 标准库运行。神经匹配需要项目虚拟环境和 PyTorch / NumPy：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-matching.txt
.\.venv\Scripts\python.exe main.py --serve
```

普通训练只生成候选，不覆盖已验证的在线权重：

```powershell
.\.venv\Scripts\python.exe tools/train_matching.py --preset wide_compact --epochs 180
```

候选写入 `output/matching_training/candidate.pt`。复现完整改进实验使用 `tools/refine_matching.py --epochs 180`：三种配置分别训练三个种子，按验证集选择，再做预先保留的确认集验收；满足晋级条件才更新 `server/models/matching.pt`。固定评估集反复使用后不能继续称其为“未见测试集”。

训练入口现在支持 `--encoder-layers 2`。一层与两层各三个种子、每个 500 轮的实测见 [Encoder 深度对照](ENCODER_DEPTH.md)，两层权重保存在实验目录，网站继续使用原有一层模型。

macOS / Linux 将解释器路径改为 `.venv/bin/python`。如果系统已装 GPU 版 PyTorch，也可使用兼容版本；本项目已在 CPU 上验证。Windows `start.bat` / `start.ps1` 优先使用项目 `.venv`，`PYTHON_BIN` 可显式覆盖。模型权重和报告保存在 `server/models/matching.pt` 与 `matching.json`，训练脚本不会读取现有用户账号、聊天或预约数据。通过网页导航“**双边匹配**”进入 `/matching`。

首次演示建议开两个浏览器会话：地陪发布服务、填写偏好；旅人填写同城需求并匹配。预置服务缺少偏好时不会自动编造偏好，请使用自己填写好的服务。

## 数据与评估边界

当前没有真实的双方接受/拒绝标签。`matching_data.py` 显式生成合成旅人和地陪，使用人工构造的不同方向偏好函数产生弱监督目标。训练得到的是教学模型，主要学习这些偏好规则及其合成文字表现，不能据此宣称超越规则匹配或实际改善成交。

当前训练人物为 96 个旅人、72 个地陪，共构造 6,912 对；模型重点拟合满足城市、服务和共同语言约束的候选。验证为 32 × 24 个独立人物，确认集为 64 × 48 个新人物。三组主题描述句模板分别隔离；结构化类别、偏好文案样式及数据生成规则仍共享，所以不代表跨真实人群泛化。词表只读取训练文本；标签直接取自生成的潜在偏好，不再反向解析文字模板。潜在的地陪擅长兴趣只用于生成标签，没有进入模型图或显式相容性特征。

确认集中 3,072 对组合有 295 对满足本合成评估的硬条件。在这 295 对上，与初版同场比较，旅人方向 MAE 从 0.2225 降至 0.1568，地陪方向从 0.1690 降至 0.0713；综合分在旅人侧／地陪侧排序的 NDCG@5 分别从 0.8926／0.9304 提升到 0.9875／0.9921。它们是合成规则蒸馏指标，不是接受率。完整对照、失败尝试、学习曲线、全组合误差及推理开销见 `OPTIMIZATION.md`。

没有硬筛时，新版全组合旅人 MAE 反而从约 0.212 增至 0.528；它专门优化合格候选，不能用于绕过硬条件的全量打分。训练误差与验证误差仍存在差距，不能宣称过拟合已彻底解决。按验证集保存最好轮次，三种子集成降低初始化敏感性。

下一步需要真实且获同意的曝光、选择、双边接受或拒绝数据；按用户和时间划分验证集，比较纯规则、仅 Transformer、仅图、组合模型的排序效果。当前测试中的文本/图移除实验只证明两部分影响输出，不证明组合模型质量更高。
